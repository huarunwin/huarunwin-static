NaïveProxy

翻墙应用商店 · 2026-11-08 · 更新于 2026-11-08

代理协议独立百科词条抗审查天花板

真浏览器级伪装 · 原生 Chromium 网络栈 · 彻底消除特征识别

由 klzgrad 开创性研发[1]，直接提取 Google Chromium 源码核心网络库（Cronet / BoringSSL）编译客户端， 通过标准 HTTP/2 或 HTTP/3 的 CONNECT 方法与前置 Web 服务器（如 Caddy forwardproxy）建立隧道[2][3]。 由于握手、指纹与流量行为与真实 Chrome 完全相同，被学术界与安全界公认为抗深度包检测（DPI）的最强标杆之一。

词条概览与核心定位

01

现代防火墙（GFW）对翻墙流量的检测已经全面超越了单纯的 IP 封锁与端口封锁阶段，转为基于TLS 指纹（JA3/JA4）、ALPN 协商、HTTP/2 帧依赖与流优先级模式、以及数据包长度时序的机器学习识别。 大多数传统代理工具（如早期的 Shadowsocks 或 VMess）由于使用专有协议头或非标准的 TLS 库实现， 很容易在公网链路上留下统计学异常特征。

NaïveProxy 采取了最为极端也是最为彻底的防识别思路：**与其在普通代码里模仿浏览器，不如直接把真正的浏览器网络模块拿来用！**作者从庞大的 Chromium 源码中剔除了无关的渲染引擎与图形界面，仅保留核心网络库编译为轻量代理客户端[4]。 在外层网络监控视角下，NaïveProxy 产生的每一个 TCP 连接、TLS 握手、HTTP/2 设置帧与普通用户使用 Google Chrome 访问境外 HTTPS 网站完全没有任何区别。

定位结论

NaïveProxy 是追求高安全性、抗封锁稳定性第一的首选协议。 虽然部署时需要自备域名与有效 TLS 证书，且依赖前置 Caddy 服务器，但其抗审查表现多年来始终处于第一梯队。

Chromium 栈与三层伪装原理

02

**1. 客户端原生 Chromium 网络栈（Cronet + BoringSSL）**从 Chromium 源码直接编译出的底层网络驱动，生成的 TLS ClientHello、Cipher Suites 排列、 TCP Window 尺度与 ALPN 参数与数十亿台设备上的真实 Google Chrome 完全相同。

2. 标准 HTTP/2 CONNECT 传输隧道与 Padding 填充完全遵循 IETF RFC 9113 规范，将目标流量封装在 HTTP/2 的二进制多路复用流中； 引入自动 padding 填充机制消除短包大小特征，对抗按包长分布进行的机器学习侧信道探测。

3. 服务端 Caddy + forwardproxy 真实 Web 托管服务端部署真实的现代化生产级 Web 服务器（Caddy），自动维护 Let's Encrypt 证书； 探测请求或常规浏览器访问只返回真实的静态网站，只有携带合法凭证的客户端才建立代理。

连接建立与数据交互流程

  1. Chromium 原生 TLS 1.3 握手客户端使用 BoringSSL 发起握手，包含最新规范扩展（如 Kyber 混合密钥套件与真实 ALPN）。
  2. HTTP/2 会话初始化与 SETTINGS 帧交换交换标准 HTTP/2 设置帧与窗口更新帧，流优先级调度树完全匹配 Chrome 浏览器的默认状态机。
  3. 发送加密 CONNECT 请求在 H2 流中发送带有 Proxy-Authorization: Basic 的请求头，申请建立到目标远程主机的端到端隧道。
  4. 服务端鉴权与透明代理转发Caddy 验证身份通过后返回 HTTP 200 Connection Established，之后双向数据通过标准 DATA 帧透明流通。

为什么它无法被机器学习识别？

审查防火墙若要将 NaïveProxy 识别为代理，就必须将特征匹配阈值设为与真实 Chrome 一致； 而这会导致全球数十亿正常使用 Chrome 浏览外网的合法 HTTPS 流量全部被误杀，这是任何骨干网过滤器都无法承担的代价。

适用场景与网络边界限制

05

最推荐使用场景：

  • **敏感时期或重点审查网络：**在大型会议、重大敏感节点或企业严格 DPI 监控网络下，NaïveProxy 具备最高的生存率。
  • **纯 TCP / 禁用 UDP 的局域网：**在高校校园网、公司局域网封锁 UDP 的环境下，NaïveProxy 基于标准 HTTPS 443 端口通行无阻。
  • **重视连接长期稳定性与隐匿性：**一个部署良好的 NaïveProxy 节点往往可以持续稳定运行数年而无需更换 IP。

不适用或受限场景：

  • **极高丢包率且无国内优化的恶劣线路：**在 20% 以上丢包的普通公网线路上，TCP 的拥塞控制会受到明显影响，此时 Hysteria 2 体验更好。
  • **零门槛新手部署：**必须自备合法域名并解析到 VPS，配置 Caddy 及相关模块有一定技术门槛。
  • **极低内存设备：**早期未经裁剪的 Chromium 二进制体积较大，在 64MB 内存的老旧路由器上运行较为吃力。

安全假设、证书依赖与局限性

06

**1. 必须使用权威机构签发的有效证书：**NaïveProxy 客户端内部严格遵循 Chromium 的安全策略， 默认开启完整的证书信任链校验与 OCSP 验证，绝对不允许使用自签证书或不受信任的证书，必须由 Let's Encrypt 或 ZeroSSL 签名。

**2. 服务端必须具备真实伪装页面：**Caddy 应当配置一个真实存在的正常站点（如静态博客或展示页），当审查系统直接向服务器发起 HTTP GET 探测时， 应当能返回标准 HTTP 200 的网页内容，不可返回空页面或异常错误。

**3. 客户端实现完整性：**若使用第三方客户端（如某些仅实现了 HTTP/2 CONNECT 却使用了 Go 语言标准 net/http 库的工具）， 其 TLS 指纹与 H2 帧序列将不再是 Chromium 真实特征，抗审查效果会大打折扣；建议务必确认客户端底层使用了真实的 Cronet 或通过验证的指纹库。
