AnyTLS + TLS

打破单一 SNI 聚类 · 动态 TLS 泛化外观 · 深度包长 Padding 混淆

由 AnyTLS 研发团队于 2024 年提出并开源[1]，针对现代审查系统对 REALITY 或 Trojan 借用的特定外部域名进行白名单排查与流量聚类分析的痛点。 在客户端动态泛化 TLS 握手特征[5]，引入智能多路会话复用（Session Multiplexing）状态机， 并对数据包实施可调整的随机混淆填充（Padding）[2]，彻底破坏数据包长度分布规律。

词条概览与核心定位

01

随着深度学习技术在网络审查系统（GFW）的广泛应用，防火墙对翻墙流量的识别不再仅仅依靠简单的端口阻断或关键词过滤。 审查系统开始采用「流量聚类分析（Traffic Clustering）」：即使流量被 TLS 加密， 但如果成千上万个客户端都长期向某几个特定借用的 SNI 域名（如微软、苹果 CDN 或小众 VPS 域名）发送固定包长比例的数据， 这些节点就会被算法归类为异常代理并进行定点干扰。

AnyTLS 的核心出发点正是打破这种特征聚类：让每次代理握手与传输都呈现出动态、离散的自然特征。 它支持客户端在握手阶段动态泛化 TLS ClientHello 参数，并在数据传输阶段对每一个数据分块进行动态可调的 Padding 填充[2]， 使得传输包长分布在统计学直方图上完全平滑，彻底消除因固定协议头导致的侧信道指纹。

定位结论

AnyTLS + TLS 属于抗高阶流量分析与机器学习审查的前沿新秀。 它已经被主流内核（sing-box 与 Mihomo）原生收录，非常适合追求技术前沿、希望摆脱单一固定伪装域名依赖的进阶玩家。

TLS 泛化外观与动态 Padding 原理

02
1. 动态 TLS 外观泛化层（AnyTLS Dynamic TLS）不拘泥于单一固定的 SNI 或握手参数，允许在合规范围内微调 TLS 扩展顺序与填充长度， 使对外流量表现为分散、多样的正常 HTTPS 访问行为，降低审查聚类风险。
2. 动态可调混淆填充层（Adaptive Packet Padding）针对握手首包、协商指令以及短 HTTP 报文进行非对称随机加盐填充； 消除根据特定数据包大小序列推断内层协议的侧信道分析。
3. 现代多路会话调度层（Session Multiplexing & Mux）在单条底层安全 TLS 连接内复用数十个并发 TCP 请求与 UDP 数据流， 减少频繁新建连接产生的额外握手时延与网络暴露面。

握手与数据交互生命周期

  1. 客户端构造泛化 ClientHello根据配置策略动态调整扩展排列与握手参数，发起标准 TLS 1.3 握手。
  2. TLS 认证与会话通道建立双端完成加密信道协商，建立安全的底层多路复用调度器。
  3. 动态加盐与随机 Padding 注入发送代理请求时，根据网络包长分布动态注入微小填充，混淆小包序列。
  4. 透明解包与目标访问转发服务端还原真实数据包并转发至目标网站，响应数据流经相同机制回传。

为什么 Padding 如此关键？

大多数代理工具的握手指令头具有固定的字节长度（例如 56 字节或 128 字节）； 现代机器学习模型专门针对这种“特征包长”进行训练。 AnyTLS 的动态 Padding 彻底打破了这一固定长度，让每个包的大小都呈现随机分布！

适用场景与网络边界限制

05

最推荐使用场景：

  • 对特征识别敏感、希望防范聚类分析的网络：在严格审查区域，动态 Padding 能显著降低被异常流量算法标记的几率。
  • 纯 TCP 网络环境：基于标准 TLS 1.3 运行，在封锁 UDP 的网络中能够稳定连通。
  • 客户端支持度良好的现代生态：使用最新版 sing-box、Mihomo 或 Shadowrocket 的用户。

不适用或受限场景：

  • 极低带宽与流量受限套餐：由于启用了动态填充，Padding 会引入少量（约 3%~8%）的冗余流量开销。
  • 要求原生 UDP 低延迟竞技：UDP 流量是通过 TCP 隧道承载，在丢包网络下的延迟波动大于基于 QUIC 的 Hysteria 2。

安全假设、证书配置与局限性

06

1. 证书与域名要求：与 Trojan 类似，AnyTLS 服务端需要配置合法的 TLS 证书（建议通过 ACME 获取公开权威证书），客户端默认进行完整性校验。

2. 填充策略合理性：默认的 Padding 填充策略是基于通用统计模型设计的； 用户无需过度调高填充上限，过大的填充只会徒增带宽浪费而不会带来线性的安全性收益。
