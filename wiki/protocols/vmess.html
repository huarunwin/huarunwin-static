VMess

首创底层传输解耦 · 现代多路复用先驱 · 经典长青协议

由 Victoria Raymond 于 2015 年设计并作为 Project V / V2Ray 的核心加密协议推出[1]。 开创性地将代理认证逻辑与底层物理传输通道（TCP、mKCP、WebSocket、HTTP/2 等）彻底解耦[2]。 历经多代演化，通过引入强制 AEAD 认证与废除 AlterID 消除历史安全短板， 是 2017–2022 年间部署最广泛的翻墙协议之一。

词条概览与核心定位

01

在 Shadowsocks 之后，GFW 开始通过针对单一端口和 IP 的持续通信分析推断代理行为。 Victoria Raymond 发起 Project V 的核心初衷，是将代理工具从单一功能的“中继器”升级为可任意自由组合的多层次网络框架。

VMess 作为这一框架的原生协议，最大的创新在于「传输层与协议层解耦」： VMess 本身只负责用户身份认证（UUID）、时钟防重放校验与数据指令打包， 而外部可以使用任何标准的传输协议来承载（例如 TCP 原始流、伪装成视频推流的 mKCP、或者与 Nginx 配合的 WebSocket + TLS）。 在 2017 到 2021 年的数次封锁潮中，“VMess + WS + TLS + CDN”一度成为无数用户防失联的最稳固防线。

定位结论

VMess 是现代代理技术演进史上承前启后的多传输组合集大成者。 虽然新部署建议优先考虑更轻量的 VLESS REALITY 或 XHTTP，但 VMess 凭借极度完善的客户端支持与海量存量节点，依然是全网不可或缺的基石。

多传输解耦与 AEAD 原理

02
1. 用户 UUID 认证与 AEAD 头部加密层采用 16 字节 UUID 进行身份识别，结合 UTC 绝对时间戳防御重放攻击； 现代规范强制使用 AEAD 头部加密，彻底消除了旧版基于散列值主动探测的安全隐患。
2. 可插拔多协议传输封装层（Pluggable Transport）原生支持 TCP、WebSocket、HTTP/2、gRPC 及 mKCP； 将 VMess 密文完全伪装成常规的 Web 流量或媒体数据包，赋予极其灵活的抗审查通道。
3. 内部多路复用与路由分流层（Mux.Cool + Routing）支持客户端在单条物理连接内并发聚合多个 TCP 代理流，降低频繁握手延迟； 结合路由规则实现海量域名与 IP 的智能国内直连与分流。

VMess AEAD 握手与请求认证

  1. 计算基于时间戳与 UUID 的认证 Auth ID利用用户 UUID 与当前 UTC 时间戳计算 16 字节认证散列，服务端核验是否在 ±90 秒误差窗口内。
  2. AEAD 头部解密与指令解析使用派生出的密钥解密包含版本号、对称加密套件、目标地址与校验码的指令头。
  3. 服务端响应头部确认服务端生成动态响应头回传客户端，双方完成双向身份相互认证。
  4. 全双工密文分块传输后续所有代理数据均通过协商出的对称算法（如 AES-128-GCM / Chacha20-Poly1305）分块传递。

为什么废除了 AlterID？

早期 VMess 使用 AlterID 派生伪装 ID 抗探针，但被证实算法安全性不足且大幅增加内存开销； 2020 年引入 AEAD 后，数学加密强度已无可挑剔，官方全面将 AlterID 废除并置为 0。

适用场景与网络边界限制

05

最推荐使用场景：

  • 存量机场节点兼容：各商业机场长期维护的万能保底节点，绝大多数老版本客户端无需更新即可直接畅连。
  • 配合 WebSocket + TLS + CDN：成熟稳定、技术方案成熟的大众化 CDN 救砖配置。
  • 多出站复杂路由代理链：在软路由或服务器上作为聚合网关节点使用。

不适用或受限场景：

  • 客户端系统时间偏差过大：若手机或电脑系统时间与标准 UTC 时间相差超过 90 秒，握手认证将全部报错失败。
  • 追求极致低延迟与低服务器开销：由于自身包含两层加密（VMess 内部对称加密 + 外层 TLS 加密），性能略逊于 VLESS。

时钟同步要求、AlterID 废除与局限性

06

1. 必须确保 NTP 时钟同步：VMess 的防重放机制深度依赖系统时钟。自建 VPS 服务端与用户客户端务必配置自动网络授时（NTP）。

2. 客户端配置务必将 AlterID 设为 0：旧版客户端默认填写的 `alterId: 64` 会强制兼容旧版伪装握手；现代所有新配置均应当填写 `alterId: 0`， 以强制启用最安全的 VMess AEAD 认证算法。
