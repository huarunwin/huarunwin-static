Thanks for this. I checked the diff statically: all 16 SHAs in actions.lock match their upstream tags, greenhat616/update-tag is the same repository as libnyanpasu/update-tag (v1.2.5 is the commit v1 already pointed at), every secret a callee reads is declared and forwarded, no caller grants less than its callee requests, and no job that pushes with git lost its credentials. Nothing blocking, but a few things to settle before merging.

1. Renovate will desync actions.lock (.github/workflows/actions.lock)

The lockfile requires every uses: ref to be listed, but renovate.json still bumps action versions with default:automergeMinor, and nothing regenerates the lock. A bump to an action ci.yml does not use (for example softprops/action-gh-release in deps-update-tag.yaml and publish.yml) passes required CI, automerges, and the next nightly or release run is then rejected. For actions ci.yml does use, every Renovate PR fails until someone runs gh actions-lock by hand; taiki-e/install-action alone releases several times a week. GitHub's docs only mention Dependabot for lockfile updates. This needs a plan (disable automerge for github-actions, or automate the relock), and the relock step belongs in docs/development/workflow.md, not only in the PR body.

2. Release, nightly, publish and daily workflows are untested

PR CI only exercises ci.yml. A caller/callee permission or secret mismatch in a reusable workflow fails the whole run at startup, so the first real validation would be the next nightly or a published release. I found no mismatch by reading, but nothing has executed.

3. Two "narrowed" refs change the action code (daily.yml, deps-build-linux.yaml)

oleksiyrudenko/gha-git-credentials v2.1 -> v2.1.2 is 17 commits ahead on a diverged history (rebuilt dist, Node 12 -> 20 runtime), and cargo-bins/cargo-binstall main -> v1.26.2 is a different commit too. The other pins resolve to the commit the major tag already pointed at. Both manifest jobs rely on the credentials action for their push, so please call these two out as upgrades rather than pins.

4. The storage publisher still receives all nine secrets per backend (target-dev-build.yaml, target-release-build.yaml)

Each of the three deps-publish-storage calls (prepare, sourceforge, telegram) forwards the full set, so the telegram job still holds SOURCEFORGE_SSH_KEY and the sourceforge and prepare jobs still hold the Telegram credentials.

5. Two actions stay on floating v1 tags

robinraju/release-downloader@v1 (deps-create-updater.yaml) and mknejp/delete-release-assets@v1 (deps-delete-releases.yaml). They are commit-locked by the lockfile, so this is mostly an inconsistency with the description.

6. git fetch --tags now runs unauthenticated (deps-create-updater.yaml)

Fine for this public repository; it would fail in a private fork or mirror.

7. Subject length

The first commit's subject is 73 characters and the PR title is 108; the repository limit is 72.
