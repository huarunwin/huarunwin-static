Open-Box：个案 FakeIP 断网源于另一 TUN 服务的网段重叠

在 Open-Box #981 的 iStoreOS 个案排查中，liandu2024 根据新版诊断包指出，relayway-cored 的 TUN 接口使用 198.18.0.0/15，与 Open-Box 的 198.19.0.0/16 FakeIP 池重叠，使流量在进入 sing-box 前被当作本机接口网段绕过。他建议停用冲突服务或调整其网段，再重启 Open-Box；当时的冲突检测清单尚未收录该服务。结论限于该帖所述环境。

作者原文@liandu2024

感谢补充新版 v0.1.479 完整诊断包，根因已经定位清楚了：

根本原因：iStoreOS 上同时运行的另一个 TUN 代理/组网服务（relayway-cored / 网卡 tun0）占用了 198.18.0.0/15 网段，与 Open-Box 的 FakeIP 地址池 198.19.0.0/16 直接重叠冲突。

诊断包中的直接证据

  1. 新版诊断包的 kernel.configMeta.buildInputs.localSubnets 直接采集到了以下本机接口网段：
    json [ "192.168.1.0/24", "172.17.0.0/16", "198.18.0.0/15" ]
    198.18.0.0/15 覆盖 198.18.0.0 ~ 198.19.255.255，把 sing-box 的 FakeIP 池 198.19.0.0/16 完整包了进去。
  2. 结合上一份诊断包的系统接口与日志，机器上同时运行着 tun0 接口以及后台进程 relayway-cored。因当前冲突检测清单尚未收录 relayway-cored，面板才没有直接弹窗阻断启动。
  3. 新版诊断包里所有可用节点探针均为 healthy，但 sing-box 内核日志中没有任何发往 198.19.x.x 的连接或报错，说明 FakeIP 流量在进入 sing-box 前就被系统当成本机/其它接口网段绕走了。

为什么会「开 FakeIP 不通、关 FakeIP 正常」

  • 开启 FakeIP 时：sing-box 为外网域名返回 198.19.0.212。但由于 198.18.0.0/15 属于本机 tun0 网卡网段，sing-box 的 auto_redirect 会将本机各接口网段加入 @inet4_local_address_set 并在拦截前直接放行（return）；数据包随后按系统路由发向非 openbox-tun 接口（tun0），最终触发 Open-Box 的 FakeIP 防泄漏守卫被丢弃（就算不丢弃，发进 relayway-cored 的 tun0 也查不到 sing-box 的 FakeIP 映射），所以完全无法访问外网。
  • 关闭 FakeIP 时：域名直接解析出真实公网 IP，不再落入 198.18.0.0/15 冲突范围内，流量正常被 sing-box 接管，因此恢复正常。

解决方法

  1. 可先在 iStoreOS 终端运行以下两条命令核实冲突接口与路由：
    sh ip addr show dev tun0 ip route show | grep 198.18
  2. 停用或卸载 relayway-cored（或将其 tun0 网段修改为不与 198.18.0.0/15 重叠的其它网段），然后重启 Open-Box，FakeIP 即可恢复正常。

附带提醒（终端 DNS）

另外你贴出的 nslookup google.com 输出中：

服务器:  UnKnown
Address:  211.139.29.170

说明这台 Windows 当前实际上是在向运营商 DNS 211.139.29.170 发 DNS 请求（因为默认网关经过旁路由，被 Open-Box 的 53 端口透明劫持后才返回了 198.19.0.212）。建议同时在 Windows 上执行 ipconfig /all 检查一下该网卡的 DNS 服务器，确认是否手动指定过静态 DNS 或需要先 ipconfig /renew 刷新 DHCP 租约，让终端直接将 DNS 指向旁路由 IP。
