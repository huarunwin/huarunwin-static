独立维护的 Android 客户端

Stelliberty Android 使用独立仓库与 Android 包名。2026 年 9 月 28 日，Kindness-Kismet 提交并合并 PR #1，更新 Mihomo 子模块、补充 Mishka 直接上游的说明，并为发布名称加入 Android 标识。该账号的实际维护行为支持这里的作品关联；Android 项目继承了 Mishka，不把上游已有代码归为该账号的原创，也不将桌面版架构或热重载能力套用到 Android 版。[1][2][3]

时代与传统客户端审美粗糙的困境

长期以来，开源代理客户端多由后端工程师主导，界面粗糙、缺少过渡动画、排版僵硬是普遍现象。在现代操作系统普及高刷新率与精致动态模糊的今天，用户对于日常挂载的代理客户端提出了更高的审美诉求。[4]

破局与设计哲学：Stelliberty Remake 的美学执念

ONEUI 秉承“视觉享受与性能兼备”的哲学，启动了 Stelliberty Remake 大版本重构。他运用现代前端与图形学优化，精心调校了每一个开关与节点卡片的弹簧动效与抗锯齿细节，让代理管理成为一种愉悦的交互体验。[4][5]

硬核工程深水区：服务模式在体热重载与跨层配置直通

在 2026 年 9 月发布的 v2.0.30 中，ONEUI 攻坚了核心重载体验：“Applying config changes in service mode now reloads the core in place, so proxies no longer drop”，消除了传统客户端切换配置必须重启内核造成的几秒网络假死。

在 commit 55ca2a0 中，他实施了关键的架构重构：“refactor(runtime): pass core configs by content across layers”，彻底消除了跨进程配置传递中的文件 I/O 损耗。[6][5]

时代余响与历史地位

Stelliberty Remake 凭借惊艳的视觉设计与顺滑无比的在体热重载技术，收获了千星好评，代表了开源客户端向现代化商业级 UI 品质演进的崭新标杆。[4][5]

ONEUI：Stelliberty 启动超时源于订阅 provider 过多且无缓存，预下载路径也与内核不一致

针对「mihomo 进程运行中但 API 无响应（External controller listen error）」，ONEUI 表示大致找到问题：订阅里 provider 很多、本地又没有缓存时，内核要在启动完成前把它们全部下载完，超过原来 10 秒的启动时限就被当成启动失败结束掉；另外导入时预下载的 provider 文件与内核实际读取的路径对不上，等于每次启动都要重新下载一遍。这两处都已修好，测试版正在构建，作者请反馈方更新后再试，看是否还会出现。
