  1. VLESS + Vision + REALITY

    通用直连优先看
    推荐评分4.5/ 5

    适合谁日常浏览、视频，希望兼顾流量特征处理与客户端选择。

    使用前提与限制

    两端支持 Vision 与 REALITY，并正确配置密钥、目标站与名称。

    这里评的是直连组合，不适用于普通 HTTP CDN；目标站与参数仍需维护。

    评分依据、客户端与来源：VLESS + Vision + REALITY

    抗识别设计5 / 5

    REALITY 处理握手与探测，Vision 针对 TLS 套 TLS 的特征做填充和转发优化。多项设计有公开说明。

    传输能力4 / 5

    优化 TLS 流量转发，可结合 XUDP；底层仍走 TCP，丢包时受 TCP 重传影响。

    客户端支持5 / 5

    Xray、sing-box 与 Mihomo 均有 VLESS / Vision / REALITY 支持，客户端选择较多。

    使用维护3 / 5

    无需为 REALITY 单独购买域名和维护常规网站证书，但密钥、目标站及版本配对需要理解。

    客户端与内核：Xray、sing-box、Mihomo 系客户端；具体应用需支持完整组合。

  2. Hysteria 2

    UDP 通畅时的弱网候选
    推荐评分4.5/ 5

    适合谁高延迟、丢包链路，以及需要同时转发 TCP 和 UDP 的应用。

    使用前提与限制

    本项按常规 QUIC / UDP 配置评分，要求客户端到服务器的 UDP 通畅。

    UDP 被封或限速时优势可能消失；带宽与拥塞控制需匹配线路。Mimic 等特殊传输另行评估。

    评分依据、客户端与来源：Hysteria 2

    抗识别设计4 / 5

    协议定义 HTTP/3 服务行为与认证后的代理语义，可选混淆；这些机制不保证 UDP 流量不会被限制。

    传输能力5 / 5

    QUIC 多流、TCP / UDP 转发与可配置拥塞控制提供了较完整的传输工具。

    客户端支持5 / 5

    有官方跨平台实现，也被 sing-box 与 Mihomo 收录；应确认使用第二代协议。

    使用维护4 / 5

    官方配置文档完整，但需配置 TLS、开放 UDP，并合理选择带宽与拥塞控制。

    客户端与内核：Hysteria 官方实现，以及 sing-box、Mihomo 等兼容实现。

    Hysteria 2 协议规范官方客户端配置sing-box 协议支持Mihomo 协议支持查看历史节点

  3. VLESS

    rprx 设计的无状态轻量代理协议，剥离协议自带加密，完全依赖底层 TLS/XTLS 握手特征。
    推荐评分4.5/ 5

    适合谁自建现代节点、追求极低 CPU 性能开销，搭配 REALITY、XHTTP、Vision 或标准 TLS 使用。

    使用前提与限制

    公网传输必须依赖外层安全层（如 TLS / REALITY / Encryption），裸奔传输无任何安全保证。

    必须与现代外层安全机制强绑定；部分老旧客户端内核不支持新型 XTLS 流控特性。

    评分依据、客户端与来源：VLESS

    抗识别设计4 / 5

    协议自身不引入多余密码学封装，完美继承外层真实 TLS 或 REALITY 的纯正握手特征。

    传输能力5 / 5

    支持 XTLS 零拷贝（Direct Read/Write），避免传统二次加解密，在大吞吐下吞吐表现拔尖。

    客户端支持5 / 5

    已成为现代科学上网事实标准协议，主流内核与移动桌面客户端均提供完整支持。

    使用维护4 / 5

    采用标准 UUID 认证；搭配 REALITY 时无需维护证书，搭配标准 TLS 则需域名证书。

    客户端与内核：Xray-core、sing-box、Mihomo、Shadowrocket、v2rayN、Loon、Surge 等。

  4. NaïveProxy

    重视浏览器流量外观
    推荐评分4.0/ 5

    适合谁以网页和其他 TCP 流量为主，愿意维护浏览器网络栈与服务端。

    使用前提与限制

    使用兼容的 Chromium 网络栈实现及配套服务端；UDP 受限时使用 HTTP/2。

    主要承载字节流。部分实现支持 UDP over TCP，需两端兼容；不等于原生 UDP 转发。

    评分依据、客户端与来源：NaïveProxy

    抗识别设计5 / 5

    复用 Chromium 网络栈，结合 HTTP CONNECT、前置服务和长度填充，针对多类指纹与探测给出设计。

    传输能力4 / 5

    HTTP/2 或 HTTP/3 多路复用，适合流式应用；UDP 能力取决于额外封装和两端实现。

    客户端支持3 / 5

    跨平台可用，但集成真实网络栈有构建要求，不能把任意 HTTPS 代理当作 NaïveProxy。

    使用维护3 / 5

    需维护证书、配套前置服务，并跟进基于 Chromium 的稳定版本。

    客户端与内核：官方 NaïveProxy 与明确集成其网络栈的客户端；sing-box 有平台及构建要求。

    NaïveProxy 设计与发布说明sing-box 平台与 UDP 支持查看历史节点

  5. AnyTLS + TLS

    支持它的客户端值得考虑
    推荐评分4.0/ 5

    适合谁希望使用 TLS、连接复用与可调整填充，且客户端已完整支持。

    使用前提与限制

    使用维护中的兼容实现并验证 TLS 证书；两端支持相同的会话与填充机制。

    默认填充只是示例；TLS 握手外观还取决于实现。UDP 通过 TCP 承载，受其重传影响。

    评分依据、客户端与来源：AnyTLS + TLS

    抗识别设计4 / 5

    可调整包长模式以缓解嵌套 TLS 特征，但协议本身不负责全部 TLS 指纹处理。

    传输能力4 / 5

    会话管理与连接复用是设计重点；支持 UDP over TCP，但不是原生 UDP 传输。

    客户端支持4 / 5

    已被 sing-box、Mihomo 及多款客户端接入，仍需核对应用版本与实现细节。

    使用维护4 / 5

    兼容内核可统一管理 TLS 和代理；示例程序及默认填充不应被当成适合所有网络的成品配置。

    客户端与内核：sing-box、Mihomo；官方说明另列了部分 Apple 平台客户端的支持情况。

    AnyTLS 官方与兼容实现AnyTLS 设计边界查看历史节点

  6. TUIC v5

    QUIC 转发的另一选择
    推荐评分4.0/ 5

    适合谁UDP 通畅，且已有成熟 TUIC v5 客户端与服务端的场景。

    使用前提与限制

    两端明确支持协议 v5，常规 QUIC 配置要求 UDP 可达。

    QUIC 不等于普通浏览器 HTTP/3；拥塞控制、UDP 模式及 0-RTT 配置需按实现核对。

    评分依据、客户端与来源：TUIC v5

    抗识别设计3 / 5

    使用 TLS 加密的 QUIC 承载；规范重点是转发机制，并不将流量定义为完整的普通 HTTP/3 网站行为。

    传输能力5 / 5

    多流转发、UDP 数据报及会话管理较完整，实现提供拥塞控制与 UDP 模式选择。

    客户端支持4 / 5

    主流综合内核有兼容实现，但旧 TUIC 代际不能直接互通。

    使用维护3 / 5

    需核对协议代际、证书、拥塞控制及 UDP 转发模式，两端参数不能只靠协议名称判断。

    客户端与内核：sing-box、Mihomo 等；协议 v5 与软件版本号不是同一件事。

    TUIC v5 规范sing-box TUIC 配置Mihomo 协议支持查看历史节点

  7. VMess

    V2Ray (Project V) 的核心自研无状态传输协议，支持模块化多路复用与多种底层承载组合。
    推荐评分4.0/ 5

    适合谁搭配 WebSocket / gRPC + TLS 通过 CDN（如 Cloudflare）进行 IP 隐藏与中继回源。

    使用前提与限制

    服务端与客户端系统时间偏差不能超过 90 秒；建议开启 VMessAEAD 保证抗重放安全。

    早期 MD5 认证头部曾被证实存在主动探测指纹；未经 TLS 保护时协议内部固定特征易被识别。

    评分依据、客户端与来源：VMess

    抗识别设计3 / 5

    搭配外层 TLS/WebSocket 时伪装良好，但纯裸协议暴露时抗被动分析能力有限。

    传输能力4 / 5

    原生支持 Mux 多路复用，并可灵活叠加 mKCP、WebSocket、HTTP/2 或 gRPC 承载。

    客户端支持5 / 5

    各大主流客户端生态完整适配，是国内机场与自建服务长期采用的标准协议之一。

    使用维护4 / 5

    采用 UUID 身份认证体系；若需搭配 CDN 则需同时维护域名与证书配置。

    客户端与内核：Xray-core、v2fly/v2ray-core、sing-box、Mihomo、Shadowrocket、v2rayN、Surge 等。

    Project V 官方 VMess 协议规范VMessAEAD 设计与强制启用说明查看历史节点

  8. Trojan

    将代理流量伪装成标准 HTTPS 流量，遭遇未知或未经认证连接时主动回退到真实网站。
    推荐评分4.0/ 5

    适合谁自备已解析公网域名并拥有合法 Let's Encrypt / ZeroSSL 证书的标准 HTTPS 代理自建。

    使用前提与限制

    需要维护域名 DNS 解析与自动化 TLS 证书申请及定期续期；443 端口需保持对外开放。

    需要持续维护域名与证书；一旦自建域名的 TLS 证书指纹或 SNI 被标记，容易被针对性阻断。

    评分依据、客户端与来源：Trojan

    抗识别设计4 / 5

    握手行为与标准 Web 服务高度一致，未授权连接主动 Fallback 到真实 HTTP 站点。

    传输能力4 / 5

    基于标准 TLS/TCP 通道，稳定性高，能无缝穿透各级严格的企业网络代理与网关。

    客户端支持5 / 5

    主流客户端内核与主流移动端工具全面集成，配置规则透明简单。

    使用维护3 / 5

    需要自行购买或托管公网域名，并负责配置自动续期的权威 TLS 证书。

    客户端与内核：Trojan-Go、Xray-core、sing-box、Mihomo、Surge、Shadowrocket、Quantumult X 等。

    Trojan 原版 GitHub 规范文档Trojan 工作机制与 Fallback 原理解析查看历史节点

  9. Hysteria 1

    基于定制 QUIC 协议的第一代面向恶劣弱网的高速代理工具，采用激进的拥塞控制抗丢包。
    推荐评分4.0/ 5

    适合谁丢包率高、跨国带宽被运营商严重限速（QoS）的恶劣网络环境下的应急提速。

    使用前提与限制

    本地与服务端 UDP 端口通畅未被运营商严重丢包或速率限制；需要配置 TLS 证书。

    QUIC 握手特征较为明显易被运营商 QoS 限制；协议已进入维护状态，官方推荐迁移到 Hysteria 2。

    评分依据、客户端与来源：Hysteria 1

    抗识别设计3 / 5

    基于标准 QUIC 格式，但发包速率特征与自定义拥塞控制在某些地区容易触发运营商 UDP QoS 惩罚。

    传输能力5 / 5

    采用 Brutal 激进拥塞控制算法，在 20%～30% 的高丢包跨洋网络下依然能跑满带宽。

    客户端支持4 / 5

    作为一代经典弱网方案拥有广泛支持，但社区新开发重心已完全转向 Hysteria 2。

    使用维护3 / 5

    需配置端口跳跃（Port Hopping）对抗运营商阻断，并需配置 TLS 证书或自签名证书。

    客户端与内核：Hysteria 1 原版内核、Mihomo、SagerNet、Matsuri、Shadowrocket 等。

  10. SSH 动态隧道

    基于 RFC 4254 规范，利用 OpenSSH 端口转发在本地建立的动态 SOCKS5 加密代理通道。
    推荐评分4.0/ 5

    适合谁拥有一台普通 VPS 时无需安装任何额外代理服务端，开箱即用的轻量紧急越障手段。

    使用前提与限制

    目标服务器开放 SSH 22 端口，客户端拥有合法的 SSH 登录凭据（密码或公钥）。

    基于单 TCP 连接隧道封装全部上层流量，遭遇弱网时会产生 TCP-over-TCP 队头阻塞；公网大流量易被限速。

    评分依据、客户端与来源：SSH 动态隧道

    抗识别设计3 / 5

    表现为合法的 SSH 握手与长连接流量，但长时间持续海量吞吐易被统计行为模型降速。

    传输能力3 / 5

    所有应用流量串行封装在单个 TCP 连接内，在弱网丢包环境下容易产生严重的队头阻塞。

    客户端支持5 / 5

    所有 Linux / macOS / Windows 系统与主流代理客户端原生支持，完全免部署服务端。

    使用维护5 / 5

    直接复用服务器原有的 SSH 登录权限，客户端一条终端命令即可启动监听。

    客户端与内核：OpenSSH (ssh -D)、PuTTY、Mihomo、sing-box、各类终端工具。

  11. MASQUE

    IETF 标准化的基于 HTTP/3 (QUIC) 的新一代代理框架，支持 CONNECT-UDP 与 CONNECT-IP 封装。
    推荐评分4.0/ 5

    适合谁依托合法标准 HTTP/3 基础设施传输 UDP 流量（如 Apple 隐私中继），具备高标准抗封锁与低握手延迟。

    使用前提与限制

    服务端与客户端均需支持 HTTP/3 (QUIC) 栈与 RFC 9298 扩展；依赖 UDP 通畅。

    生态处于早期推广阶段，仅部分新版本代理内核与专用网络服务提供完整支持；部署门槛较高。

    评分依据、客户端与来源：MASQUE

    抗识别设计5 / 5

    完全遵循 IETF 开放标准 HTTP/3 与 WebTransport 格式，流量在外部观测与正常主流网站无异。

    传输能力5 / 5

    基于 QUIC 原生数据报（Datagram）承载 UDP，无队头阻塞，握手延时低且具备极速恢复能力。

    客户端支持3 / 5

    苹果生态深度支持，开源翻墙客户端目前集中在 sing-box 与 Mihomo 最新开发分支。

    使用维护2 / 5

    依赖完整的 HTTP/3 服务端环境与合法证书链，配置参数与鉴权验证相对严格。

    客户端与内核：Apple iCloud Private Relay、sing-box、Mihomo、Cloudflare WARP/Zero Trust。

  12. ShadowQUIC

    结合 Shadowsocks AEAD 加密认证与 QUIC 传输层握手混淆的多路复用抗阻断协议。
    推荐评分4.0/ 5

    适合谁希望利用 QUIC 的单连接多路复用与抗弱网丢包优势，同时规避标准 TLS 证书维护与握手特征的场景。

    使用前提与限制

    通信双方 UDP 端口通畅；需配置一致的密码与混淆参数。

    缺乏大型工业级标准化审查；若所在地区运营商对 UDP 实施严苛限速，实际表现可能劣于 TCP 方案。

    评分依据、客户端与来源：ShadowQUIC

    抗识别设计4 / 5

    改造 QUIC 握手包头结构，消除固定版本协商与明文特征，有效防御常规 DPI 探测。

    传输能力5 / 5

    继承 QUIC 的连接迁移（Connection Migration）与多路复用机制，弱网切换 Wi-Fi/蜂窝不中断。

    客户端支持2 / 5

    新兴小众自研协议，主要由 MetaCubeX / Mihomo 生态提供早期实验性支持。

    使用维护4 / 5

    采用类预共享密钥机制，省去申请与管理真实域名的运维流程。

    客户端与内核：ShadowQUIC 官方实现、Mihomo 等前沿代理内核。

    ShadowQUIC 官方项目规范与发布Mihomo 官方代理协议配置手册查看历史节点

  13. Tailscale

    基于 WireGuard 内核、DERP 全球中继与 Disco 协议构建的零配置点对点网状（Mesh）组网系统。
    推荐评分4.0/ 5

    适合谁个人多设备无公网 IP 互联、内网穿透访问异地 NAS、或通过 Exit Node（出口节点）进行科学分流。

    使用前提与限制

    需注册 Tailscale 账号（或部署自建 Headscale 控制平面）；设备间需建立 NAT 穿透通道。

    依赖中心化控制面分发密钥；直连流量外观为 WireGuard UDP，跨国节点若穿透失败回退 DERP 会增加延迟。

    评分依据、客户端与来源：Tailscale

    抗识别设计2 / 5

    节点直连时为原生 WireGuard UDP 数据包，穿透失败回退 DERP 时为标准 HTTPS WebSocket 流量。

    传输能力5 / 5

    支持 STUN/ICE 智能 NAT 穿透与多节点点对点全网状互通，穿透成功后直连延迟最低。

    客户端支持5 / 5

    商业端覆盖全平台（包含电视盒与 NAS），Mihomo 等代理内核也已内置出站支持。

    使用维护5 / 5

    全自动分配 100.x 内网 IP 并通过协调服务器管理密钥交换，日常几乎零维护负担。

    客户端与内核：Tailscale 全平台官方客户端、Mihomo 内置 tailscale 支持、Headscale 开源服务端。

  14. VLESS + XHTTP + TLS

这份推荐分是怎么算的？

以个人日常代理选型为范围，四项各给 1–5 分，2 分和 4 分表示相邻档位之间。 综合分 = 各项分数 × 权重后相加，四舍五入到 0.5 分；同分不分先后。 网络前提不满足时，再高的分数也不适用。高分表示更值得在所列场景中考虑，不表示更难被封锁的实测结论。

抗识别设计35%

看公开设计如何处理握手、探测与流量特征；不代表实测抗封锁率。

1 分：缺少针对性设计；3 分：有部分措施；5 分：有多项具体且公开的应对机制。

传输能力25%

看 TCP / UDP 转发、复用与弱网机制；网络能否连接另列为使用前提。

1 分：用途受限；3 分：满足常规转发；5 分：TCP / UDP 能力及传输控制较完整。

客户端支持25%

看现有内核、客户端与平台支持；支持内核不等于每个应用都已更新。

1 分：实现很少；3 分：有可用实现但选择受限；5 分：多个主流内核与客户端支持。

使用维护15%

看部署步骤、证书、版本配对与日常维护负担；越省心分数越高。

1 分：复杂或实验性强；3 分：需维护若干组件或参数；5 分：配置与维护较简单。

每项评分是本站编辑判断；引用用于核对机制与支持情况，原作者并未给出这些分数。线路质量、服务器负载、IP 可达性与配置都会改变实际体验。

其他协议怎么选？
WireGuard / OpenVPN / IKEv2
适合 VPN、远程接入和组网，目标与本表的日常抗审查代理选型不同，暂不混入评分。参见 VPN 历史与官方资料。
Tor obfs4 / Snowflake / meek
用于接入 Tor；需要 Tor 的匿名路由时再按其接入条件选择。参见 Tor 传输与官方资料。
SOCKS5 / HTTP CONNECT / MTProxy
前两者常用作本地接口或代理基础能力；MTProxy 服务于 Telegram。用途不同，不能单凭名称替代本表中的完整组合。参见 通用代理、MTProxy。
VMess AEAD
VMess 需区分旧认证方式与 AEAD，不能因协议出现较早就一概归为旧方案。 选型还要看搭配的传输、安全层及两端实现；已有稳定环境可继续按需使用。参见 VMess AEAD 的代际说明与官方资料。
VMess AEAD + HTTPUpgrade + TLS

VMess 负责代理认证与转发，HTTPUpgrade 负责 HTTP/1.1 升级后的连接承载，TLS 提供外层保护。适合两端支持完整组合、使用兼容 CDN 或 Nginx 反代且线路实测稳定的环境；需校验 TLS 证书，并确认中间服务的升级请求支持、超时和服务规则。

Xray 官方 HTTPUpgrade 文档说明它省去 WebSocket 的其他协议部分，可减少封装开销，并提示流量特征、 建议换用 XHTTP。未启用 ECH 时，握手中的 http/1.1 ALPN 是其提示的特征之一；启用 ECH 后需区分内外握手，见下方说明。 这些设计差异不能直接推导出跨线路速度或抗封锁率排名。

暂不评分：尚未完成与上表同等的组合兼容性及维护评估，也没有跨线路对比实测。 具体体验取决于线路、CDN、客户端与配置；支持 VMess 不等于支持 HTTPUpgrade。参见 Xray 官方 VMess 配置文档。

HTTPUpgrade + ECH + Cloudflare

ECH 加密部分 TLS 握手信息，保护客户端到 Cloudflare 边缘这一段的真实 SNI。需客户端实现与版本支持 ECH、站点边缘启用 ECH，并取得有效的 ECHConfig；只打开站点开关不能证明客户端已成功协商。Cloudflare 官方说明也指出，网络中间方仍可看出连接到了 Cloudflare。

Xray 现行 TLS 文档明确：其 uTLS 实现启用 ECH 时，外部 ALPN 显示为 h2,http/1.1， HTTPUpgrade 的 http/1.1 放在加密的内部握手中。 因此不能继续把该内部值当作明文可见特征；这也不代表流量大小、时序等特征全部消失。

ECH 提供握手隐私，不增加 CDN 配额或改变服务规则，也不保证提速、连接成功或免于封锁。 它不负责 Cloudflare 到源站这一段的安全配置；DNS 查询的隐私也需另行考虑。 本页不据此提高组合评分。
